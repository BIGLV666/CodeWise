# 判题链路压测报告（2026-09-12）

## 背景与目的

在 Docker 全栈（单机 8 核 / Docker VM 8GB，桌面级开发环境）上对判题主链路做吞吐上限探测：
验证 MQ 削峰、容器池、CAS 幂等、事务性 Outbox 在真实负载下的正确性，定位吞吐瓶颈并量化改造收益。

## 方法

- 负载生成：固定并发 HTTP 客户端经网关突发提交（100~150 发/轮），负载混合 AC/WA/CE/TLE 四类场景；
- 判题执行：RabbitMQ 异步消费，Docker 容器池逐题判题；
- 结果核对：以数据库终态为准（非客户端返回），核对零 `judging` 残留、零死信堆积、结果分类与提交意图一致；
- 逐级加压：消费并发 1→2→4→8，容器池 2→2→4→6，每档测量排空吞吐。

## 结果：四档证据链

| 配置（消费并发 + 池容量） | 排空 100 发 | 吞吐 | 关键观察 |
| --- | --- | --- | --- |
| 1 + 2（改造前基线） | ~170s | ~35 条/分 | **第二个容器全程闲置**——消费者并发隐式为 1，池形同虚设 |
| 2 + 2 | ~90s | ~67 条/分 | 1.9×，容器池开始被真正利用 |
| 4 + 4 | ~58s | ~103 条/分 | 4 容器全程满载，近线性 |
| 8 + 6 | 150 发 ~36s | ~250 条/分 | waiting=2（消费超配池，队列按设计兜底） |

接入层远未到瓶颈：100 发并发突发在 768ms 内全部入队（130 rps，p99 84ms），判题执行才是约束。

## 理论模型与校验

```
吞吐 = min(消费并发, 池容量, CPU 核数/1.6核秒, 内存余量/每沙箱~0.25GB) ÷ T单题
T单题 ≈ javac 编译 0.8–1.2s + 3 测试点运行 0.5–0.8s + 开销 0.1–0.2s ≈ 1.5–2.2s（实测单消费期 1.7s）
```

四档实测全部落在理论区间（预测 35/70/120/250 vs 实测 35/67/103/250）。
本机剩余约束为内存（≈10–13 并发沙箱），理论极限 ≈300±30 条/分，已达到 ~85%。

## 压测发现并修复的问题

1. 判题消费者并发隐式为 1，容器池容量与消费能力错配 → 并发改为可配置（`JUDGE_CONCURRENCY`），并与池容量联动约束写入代码注释；
2. AI 建议通知使用默认 SimpleMessageConverter 发送不可序列化 DTO，真实模型生成成功后整条事件被当毒消息死信 → 统一 Jackson2JsonMessageConverter；
3. SSE 解析仅兼容 `data: `（带空格）格式，部分网关省略空格导致回复静默截断 → 兼容两种格式；
4. 模型空响应（网关限流）被按成功落库为空消息 → 空响应守卫置 FAILED 走重试/死信。

正确性结论：450 条混合负载全程零消息丢失、零 `judging` 残留、判题结果分类与提交代码意图完全一致；
AI 建议链路在无模型/模型限流场景下按设计重试 3 次后死信留痕，可人工重放。

## 局限与后续

- 单机环境，数字不代表集群水位；吞吐公式水平可扩展（每加一台判题 host 约 +250 条/分）；
- 瓶颈按序出现在：消费并发 → 容器池 → 宿主 CPU/内存。下一步优化方向：编译结果按代码哈希缓存（T 单题可从 ~1.7s 降至 ~0.6s）、AI 建议消费并发化（当前单条 14–20s，WA 高发时先于判题饱和）。
